- Q: Issue #142 (spike) — should the vendored `http_parser` (Joyent/nodejs http-parser 2.5.0 at `src/mmt_tcpip/lib/http_parser.{c,h}`) be updated or replaced? Is there a CVE/deprecation driver, and what is used for HTTP/2?
  A (spike): Keep the vendored parser but bump it to the final upstream release 2.9.4 (Mar 2020). Findings: (1) Current 2.5.0 is 9 years behind HEAD; upstream is now archived and explicitly recommends llhttp for new projects, but llhttp is TS-generated and not a drop-in (different API, rewrite of `http_parser_integration.c` + `proto_http.c` required — high risk, fingerprint impact). (2) 2.5.0→2.9.4 fixes that matter to DPI: OOB read via `strtoul` in `http_parser_parse_url()` (9ce7316, not on the hot path — `proto_http.c:383` only calls `http_parser_execute()` and `request_url_cb` is a no-op — but still reachable), strict `Content-Length` blank/empty rejection (01da95f/3502589, prevents request-smuggling-tolerant parsing), nread accounting and pointer-arithmetic fixes. No CVEs were issued but the fixes are security-hardening. (3) HTTP/2 is NOT parsed by `http_parser`; `src/mmt_tcpip/lib/protocols/http2.c:18` uses a bespoke frame parser (`http2_can_read()` bounds checks added in #146) so no dependency. (4) Bump is trivial and ABI-compatible: only `src/mmt_tcpip/lib/http_parser.h:8-10` version macros and the vendored `.c` change; `http_parser_init`/`http_parser_execute`/`HTTP_PARSER_ERRNO`/`parser->upgrade` contract is unchanged and SDK builds clean (`make -C sdk -j`). Decision: bump to 2.9.4 now, defer llhttp migration unless a future CVE or fingerprint requirement forces it.
  Source: `src/mmt_tcpip/lib/http_parser.h:8-10`, `src/mmt_tcpip/lib/http_parser.c` (vendored 2.5.0 vs nodejs/http-parser@2.9.4), `src/mmt_tcpip/lib/protocols/proto_http.c:372-390`, `src/mmt_tcpip/lib/http_parser_integration.{h,c}`, `src/mmt_tcpip/lib/protocols/http2.c:12-18`, nodejs/http-parser README deprecation notice + tags `v2.5.0`→`v2.9.4` (76 commits).

- Q: Issue #379 (F-PERF-001) — how should the interned-IPv6-address store hash all 16 address bytes, be keyed per handler, and bound collision work?
  A: Three coordinated changes. (1) `ipv6_addr_hash()` folded `w[0] ^ (w[1] << 1)` — the shift dropped `w[1]`'s top bit so 1 of the 128 address bits never reached the bucket index, and the XOR let correlated differences cancel into the same bucket; both 64-bit words now feed independent multiplies plus a one-step finalizer (same shape as `ipv6_session_hash()`, still consistent with `ipv6_addr_comp`'s memcmp equivalence). (2) `mmt_oa_table` gained a `seed` field mixed into `hash_of()` (`mmt_mix64(hash(k) ^ seed)`), drawn per table from a process-local counter decorrelated through fmix64 — two maps are keyed independently (a collision set computed for one handler's table does not transfer) while staying deterministic across runs because table creation order is fixed, which the golden classification fingerprint and reproducible tests rely on. (3) `mmt_oa_insert`'s probe loop is now explicitly bounded by `cap` (matching find/update/remove) and fails when a full scan finds no EMPTY terminator — unreachable under the `used < cap` invariant, so it is defense-in-depth, not a semantic change. - Q: Issue #380 (F-PERF-002) — how does TCP reassembly keep duplicate offers allocation-free, and what does the per-flow `tcp_reassembly_limit` bound?
  A: Two coordinated changes. (1) `tcp_reasm_offer()` now finds the insert position — tail append, tail/head equality, head prepend, or an interior `tcp_seg_locate()` walk (the `tcp_seg_insert()` walk without a node, one visit per node examined, so the #245 visit accounting is unchanged) — BEFORE carving; a duplicate sequence number is dropped and counted once without touching the block chain. Previously the carve came first and the release of a duplicate only decremented the block's live count, so every duplicate burned head-block bump space: 1,024 retained one-byte segments each followed by 169 duplicates allocated 1,024 blocks (16,809,984 B, 1,025 allocator calls) while `live` stayed ~98 KB; now 7 blocks (114,912 B, 8 calls — the same as without duplicates). This also settles the #245 duplicate-policy TODO: the first segment wins. (2) The limit now bounds reserved storage, not content: `mmt_tcp_reasm_t.reserved` = Σ(block header + cap) + both image capacities, maintained by `mmt_segblk_carve/release/free_all` and the image realloc; `live` stays the content gauge (`content <= reserved <= limit`). Admission requires `reserved (+ any new block) + owed[0] + owed[1] <= limit`, where `owed[d] = max(0, image_len + pending_len - image_cap)` is the image growth still needed to flatten the direction's pending bytes; a new block is right-sized to the remaining room (never below the aligned carve), and an emptied head block that the carve does not fit is freed first and credited to that room (otherwise it stayed behind the new head, reserved until teardown), and image growth (x4 geometric) is clamped to `cap_max = limit - (reserved - image_cap[dir]) - owed[!dir]`. Review follow-up: the speculative part of a growth step — beyond the direction's `image_len + pending_len` — takes at most half of what `cap_max` leaves free, and an offer the invariant would refuse first trims both images' idle capacity (beyond `image_len + pending_len`, 16-B rounded) with a shrinking realloc and credits `reserved` (a failed shrink keeps the buffer and accounting), then recomputes `owed` — the trimmed cap excludes the arriving segment — before re-checking admission. Without this, one direction passing 1 MiB reserved nearly the whole budget as empty capacity and starved the other (a keep-alive request after a 1.46 MB response lost 137 of 200 segments; a peer that sent 1.08 MB and stopped capped the other side at 1 MiB). Trimming happens only at packet arrival, the same pointer contract the growth realloc already relies on (readers hold an image pointer only within the current packet callback). Under that invariant a drain can always absorb what was admitted, so images stay gap-free; if the limit is lowered mid-flow, new reservations are refused and the drain keeps what fits and drops (counts) the rest — a budget clamp is reported distinctly from realloc OOM, which still re-links the segment. Exhaustion policy: offers that would break the budget are dropped and counted in `mmt_tcp_reasm_bytes_dropped()`; teardown frees every block, both images and the state. Metadata is reported separately and not charged: the per-flow `mmt_tcp_reasm_t` (120 B on LP64) and transient realloc copies. Alternatives rejected: a pure clamp of block + image bytes without the owed headroom (admitted pending bytes could then be unflattenable — a wedged drain or silent gaps — and would churn blocks); a new public knob or a global reserved-bytes gauge (public ABI growth for no extra guarantee — the existing `set_tcp_reassembly_limit()` is the budget); compacting partially-dead blocks (copies and pointer fix-ups on the packet path, unnecessary once duplicates never carve). Measured with the new `tcp-memory` fixture at the 4 MiB budget: AC1 workload 8 allocations / 114,912 B reserved; 8,129-B undrained segments peak 2,804,240 B (HEAD: 8,372,160 B); two-direction and image+pending streams peak at most 4,194,304 B (HEAD: 8,503,520 / 5,835,904 B); all admitted bytes flattened in order; the fairness cases (keep-alive, idle peer) refuse nothing until content is within 256 KiB of the budget, and a single in-order stream filled to the budget reallocates its image 17 times. `tools/phase0/tests/run_tcp_reassembly_perf_test.sh` still passes (0 in-order/reversed visits, duplicates dropped once, 64 KiB ceiling respected, teardown gauge 0).

- Q: Issue #381 (F-PERF-003, first part) — before the pending-segment insertion structure changes, what exactly does TCP reassembly emit for in-order, reversed, interleaved, duplicate, overlapping, 32-bit-wrapped, partially consumed and torn-down streams?

- Q: Issue #382 (F-PERF-003, second part) — how is out-of-order insertion into the TCP pending-segment store bounded?
  A: With an index, not a capacity limit: every characterized workload stays fully accepted. Interior inserts in `tcp_reasm_offer()` now locate their position through an insert-only AVL index over the pending list (`tcp_seg_idx_locate()` / `tcp_seg_idx_link()`, children and height carried in `tcp_seg_t`, root in `mmt_tcp_reasm_t.seg_root[dir]`) instead of the `tcp_seg_locate()` list walk. The list stays the source of truth for drain order; the tail-append and head-prepend fast paths still touch neither structure (0 visits), and `tcp_seg_idx_sync()` indexes those nodes lazily the next time an interior lookup needs the index — an empty index is built from the sorted list in O(n), otherwise the unindexed head prefix and tail suffix are inserted — so each node is indexed at most once. The locate path is recorded and reused to link the node after admission and carving (neither relinks pending segments), so a lookup is one O(log n) descent; duplicates are still refused before any carve. Ordering is `tcp_seq_before()`, consistent only while pending seqs span less than 2^31 (the same precondition as the list walk); beyond it the insert position is unspecified, but a sync always links every node — even one whose seq repeats an indexed node, which a head prepend can add in that regime — so no node stays unindexed and is re-walked by every later sync (QA review: skipping such nodes let 8,192 stuck prepends cost 813,294,061 visits; now 223,399). The drain drops the index with the list, and an image OOM that re-links a suffix resets it (heights cleared) for a lazy rebuild. - Q: Issue #383 (F-PERF-004) — how does the IPv4/IPv6 fragment map pick its eviction victim at the 1,024-datagram ceiling without walking the whole map on every arrival?
  A: With a maintained recency order. Every in-flight datagram embeds an intrusive `mmt_hlru_t` node (prev/next plus its map key) in the prefix shared by `ip_dgram_t` and `ipv6_dgram_t`; the circular list's sentinel lives on the handler (`ip_streams_lru`, `ip6_streams_lru`; the zeroed handler reads as an empty list). The victim is therefore the least recently *updated* datagram: with non-decreasing packet timestamps that is exactly the old smallest-`last_activity` choice (ties, previously hash-walk order, are now the earliest updated), while a timestamp that runs backwards has no effect of its own: the update moves the datagram to the tail like any other, whereas the old scan would evict it next. The age sweep still walks the map once per expiry second; it is off the arrival path, and (unchanged by #383) `packet_session.c` only runs it on `ip_streams` — `ip6_streams` datagrams leave by completion, ceiling eviction or handler close. Measured: 10,000 replacement arrivals at the ceiling examine 10,000 victims (the old scan: 10,240,000 walker callbacks), make 0 walker callbacks and 20,000 index operations. Alternative rejected: a timestamp-ordered min-heap (keeps min-timestamp semantics under backwards clocks but costs O(log n) per fragment and a per-map array to allocate and free).
